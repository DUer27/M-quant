## Goal
在现有 M-quant 策略开发平台之外，建立一个隔离、可运行、面向 A 股股票/ETF 实战的执行框架骨架，优先复用成熟开源交易框架的设计与适配边界；M-quant 负责因子、策略、回测和信号生成，新框架负责信号接收、风控、模拟订单、持仓与成交账本，为后续接入 VeighNa/券商或其他 A 股 Gateway 做准备。

第一阶段以 Paper Broker 为唯一执行后端，完成从 M-quant 标准信号到模拟订单、成交、持仓和账户状态的闭环；后续真实小额交易只能通过明确的适配器和安全开关启用。

## Acceptance criteria
- [ ] 新框架位于独立目录/模块，不修改 M-quant 现有策略研究逻辑，不把真实下单代码混入现有前端或研究 API。
- [ ] 提供清晰的启动方式，新环境可按项目文档启动服务或命令行入口，并能完成一次端到端 Paper Broker 演示。
- [ ] 定义并校验版本化的标准信号格式，至少包含策略标识、信号时间、标的、目标仓位或订单意图、数据口径和风险参数；非法或过期信号会被拒绝并记录原因。
- [ ] Paper Broker 支持模拟账户现金、持仓、订单、成交、手续费/滑点、订单状态和可追溯账本；重复提交同一信号不会重复下单。
- [ ] 具备最小可用的 A 股/ETF 交易规则边界：交易时段校验、整手/最小交易单位校验、买入资金校验、卖出持仓校验、停牌/不可交易状态拒单接口，以及 T+1 规则的可扩展位置；不能用“全部允许成交”冒充完整实盘规则。
- [ ] 具备基础风控门禁：单标的最大权重、单笔最大金额、最大换手/订单数量、现金保留比例和总开关；触发门禁时不产生模拟成交。
- [ ] M-quant 与新框架采用文件/JSON 作为第一阶段集成方式，并预留 REST/API 边界；文档明确两边职责、信号 schema、导入目录和错误处理方式。
- [ ] 默认永远运行在 Paper 模式；代码、配置和文档中没有默认真实下单路径、真实 API Key 或真实券商凭据；未来 Live 模式必须有显式配置和安全开关。
- [ ] 提供自动化测试，覆盖信号校验、幂等、风控拒单、资金/持仓校验、手续费/滑点、订单状态流转和最小交易规则；测试命令可重复执行并通过。
- [ ] 提供本地预览或可观察接口，能够展示账户、持仓、订单、成交、风控拒单和运行状态；关键数据不能用随机 mock 伪造为实盘结果。
- [ ] 最终报告说明选用的开源框架/设计参考、许可证注意事项、当前已实现能力、尚未实现的券商 Gateway、从 Paper 到真实小额交易前必须完成的清单。

## Boundaries
- [ ] 本轮不连接任何真实券商、交易所或真实账户，不发送真实买卖、撤单或资金操作请求。
- [ ] 本轮不声称任何策略盈利，不把历史回测、模拟成交或演示数据包装成实盘业绩。
- [ ] 不覆盖或重写现有 M-quant 的研究数据、策略结果和前端行为；除非为集成说明新增最小文档或样例文件。
- [ ] 不复制受许可证限制的代码；只在许可证允许的范围内复用开源依赖、接口思想或明确标注来源的代码。
- [ ] 不引入真实凭据、硬编码本机绝对路径或不可审计的后台自动下单任务。
- [ ] 真实小额交易适配器、券商选择、生产部署和资金启用属于后续阶段，必须在 Paper 验收通过后单独确认。
