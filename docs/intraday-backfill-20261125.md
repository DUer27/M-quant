# 独立补采队列第一批

日期：2026-11-25，北京时间。已部署本地平台。统一连续验收按用户要求继续推迟，本批没有新建或重置验收窗口。

## 范围与入口

数据采集中心 → 质量与记录 →“独立补采队列”。可查看排队、有限重试、候选已取得、后续采集已覆盖、跨日待来源及边界待复核状态；可单独暂停补采或在休市执行一项。

先跟踪原有3只分钟核查样本000001、000002、000063。最新采集完成后，只将同一来源、股票、日期、复权口径的内部疑似缺口排队，不在最新采集进程内请求历史数据。午休不算缺口，未知开收盘边界不补造数据，长段按每项最多30个候选标签拆分。

当前适配器只取来源当前返回的分钟序列，未接入指定历史日期查询。因此自动补采限当日范围；跨日任务显示“需要历史分钟来源”，不会用今天的数据冒充历史。补回的只是待核实候选，闭合语义和交易状态仍需确认。

## 调度、恢复与代价控制

- 补采使用独立进程和独立SQLite队列，在已确认的休市时段执行；交易时段及日历不明时让路。平台每分钟最多启动一项，每次最多一次外部请求，每日上限20次；初始待执行队列最多100项。
- 与最新采集共用运行锁、来源冷却和实际请求时间。两进程不并发争用来源，追加限速仍为至少0.6秒。补采独立开关不等于最新采集开关。
- 手动最新采集或交易时段到来时，控制器要求补采退出；确认退出后才启动最新任务。补采进程超过20秒会结束；单次连接/读取超时为2/3秒。这是有界处理与优先调度，不是跨进程零延迟保证。
- 中断任务租约过期后重新排队；尝试次数和日额度在请求前预占，中断也计入，避免重启后无限重试。每项最多3次实际或中断尝试，超过后待人工核查；失败间隔至少5分钟。供应商限流继续遵守Retry-After并更新共享来源冷却。
- 同一缺口去重；后续正常采集或同一次同源补采响应已覆盖其他任务时直接消单，避免再请求。来源不同不能混合补齐。
- 候选只保存于独立backfill.sqlite的observations表，记录来源、目标标签、收到时间及任务编号，强制closure_verified=false、strategy_eligible=false。不会覆盖minute-cache、报价缓存、主运行状态或正式闭合数据表。
- 本批增加了队列数据库、短事务和状态文件，正常采集末尾也有少量排队成本；没有测得长期增量耗时。不引入自动删历史、云服务或永久原始响应保存。
